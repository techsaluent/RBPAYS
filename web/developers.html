Conventions

The rules that hold for every endpoint below. Read once, then skim the services.

Authentication

Send Authorization: Bearer <token>. A token is either an interactive JWT (member/staff login) or a staff API key tpk_… for AI-agent / n8n automation.

Idempotency

Optionally send Idempotency-Key: <your-ref> (or a reference in the body). Re-sending the same key returns the original transaction — no double charge.

Amounts

Send amount in rupees (e.g. 990 or 99.50). The ledger stores integer paise. An optional charge (rupees) applies only when no commission rule matches.

Platform reference

Every transaction gets a unique 15-character uppercase code (A–Z 0–9, no prefix), e.g. 2LNYKFTLYRJ5CFF. The bank UTR arrives later on the callback.

Response envelope

Every service POST returns the same shape — 201 Created for a new transaction, 200 OK when an idempotent replay returns the original. The status may be pending until a provider callback settles it.

// 201 Created
{
  "transaction": {
    "id": "a1b2c3d4-…",           // master txn id (use for receipts/refunds)
    "reference": "2LNYKFTLYRJ5CFF",  // 15-char platform reference
    "status": "success",           // success | pending | failed
    "amount_paise": 99000,         // ₹990.00
    "charge_paise": 0,
    "utr": null                    // filled from the provider callback
  },
  "idempotent": false
}
Pending is normal. Where a provider settles asynchronously (payout, DMT, UPI…), the POST returns status:"pending" and the wallet is already reserved. The final callback flips it to success or reverses it on failed — see Success / pending / failed.

Errors & duplicate guard

Error shape

{
  "error": {
    "message": "Insufficient balance",
    "details": null
  }
}

Status codes

200/201OK / created
401missing / invalid token
403not permitted (IP / role / secret)
409duplicate transaction blocked
422risk / AML block
409 — duplicate guard. The same member sending the same service, amount and details (account / VPA / consumer no.) again within the admin window (default 5 min, 0 = off) is rejected. A previous failed attempt never blocks a retry; changing any detail passes straight through.

Callback format

Sign the raw body and send the hex digest as a header. Only reference and status are required — the many field-name and status spellings Indian aggregators use are all accepted.

Signature

X-Webhook-Signature: HMAC_SHA256(rawBody, secret)   // hex; a "sha256=" prefix is also accepted

Request body

{
  "reference":    "2LNYKFTLYRJ5CFF",   // our 15-char ref, echoed back
  "service":      "payout",            // optional — derived from reference
  "status":       "success",
  "provider_ref": "PSP123456789",
  "utr":          "SBIN0XXXXXXXX",
  "message":      "Payout credited to beneficiary"
}

Response

{ "status":"ok", "reference":"2LNYKFTLYRJ5CFF",
  "settled":"success" }

// replayed callback (idempotent):
{ "status":"duplicate" }

Accepted field aliases

CanonicalAlso accepted
referenceclient_ref, clientRef, client_reference, reference_id, referenceId, refid, ref, orderid, order_id, clientReferenceNo
statustxn_status, txnStatus, transaction_status, state, response_status
utrbank_ref, bankRef, rrn, bank_utr
provider_refproviderRef, txnid, txn_id, transaction_id, operator_ref, operatorId, opid

Signed callback — cURL

# body is the exact bytes you sign
BODY='{"reference":"2LNYKFTLYRJ5CFF","status":"success","utr":"AXISN1234567890"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" | awk '{print $2}')

curl -X POST https://tutipays.com/api/v1/webhooks/provider/<providerId> \
  -H "Content-Type: application/json" \
  -H "X-Webhook-Signature: $SIG" \
  -d "$BODY"

Success · pending · failed

The status you send is normalised to one of three outcomes, each with a defined effect on the member's wallet.

success

Settle & pay commission

Marks the transaction successful, records the utr, and pays the retailer / distributor / MD commission up the chain.

pending

Hold, no wallet change

Recorded as interim. The reserved amount stays held; nothing moves until a final success or failed callback arrives.

failed

Auto-reverse in full

Reverses the entire wallet deduction back to the payer (₹990 out → ₹990 back) and marks it failed. No partial reversals.

Exact payload for each status

Same URL, same signature header — only status changes. Request on the left (what the provider POSTs), response on the right (what TutiPays returns).

Status spellings accepted

You send (any of)Normalises to
success, successful, true, 1, completed, complete, processed, paid, settled, acceptedsuccess
pending, processing, initiated, queued, inprocess, 2, (anything unrecognised)pending
failed, failure, fail, false, 0, rejected, error, declined, reversed, refunded, bounced, cancelledfailed
Terminal is terminal. Once a transaction is success or failed, a later callback is a safe no-op (returns ok without moving money again). To reverse a settled transaction, use the admin refund flow.
